# План «Стабильный ДНК: Атомарная Архитектура»

Пошаговый план правок по файлам. Без внесения изменений в код — только план.

---

## Цели

1. **Атомарность замены** — убрать «матрёшки» при Retranslate only these (single-pass, без повторного матча вставленного текста).
2. **Строгий контракт DNA** — Zod-валидация и нормализация (приведение к `{ longForm, shortForm }`).
3. **Заморозка DNA при патче** — явный контракт и проверка, что DNA не перезагружается во время patchTranslate.
4. **Pre-flight проверка на циклы** — предупреждение о риске рекурсии (key внутри value, циклы в графе ключей).

---

## Шаг 1. Single-Pass замена в translation.service.ts

**Файл:** `backend/src/services/translation.service.ts`

**Что делать:**

1.1. Добавить функцию **`buildReplacementPairsWithPlaceholders`** (или расширить использование существующей логики):
   - На вход: `abbreviationLogic`, опция `usePlaceholders: true`.
   - Выход: массив пар `{ pattern, target }`, отсортированный по убыванию длины `pattern` (чтобы длинные ключи матчились первыми).
   - Использовать тот же порядок ключей, что и в `buildReplacementPairs`, без изменения семантики.

1.2. Реализовать **двухфазную замену** внутри `applyTotalCyrillicBan`:
   - **Фаза 1:** один проход по тексту: для каждой пары (pattern → target) заменить все вхождения pattern на плейсхолдер `\uE000${index}\uE000` (или один общий префикс/суффикс с индексом). Важно: искать только **непересекающиеся** вхождения (после каждой замены сдвигать позицию поиска за конец вставленного плейсхолдера). Либо собирать все матчи по позициям, сортировать по start, разрешать перекрытия (оставлять самое длинное совпадение), заменять с конца к началу.
   - **Фаза 2:** заменить каждый плейсхолдер на соответствующий `target`. Так вставленный target никогда не сканируется снова.

1.3. Сохранить текущее поведение для **untranslatableKeys** и **Cyrillic removal** (skipCyrillicRemoval при targetLocale ru): применять их к результату после фазы 2.

1.4. Убедиться, что **`applyDnaFuzzyMatch`** вызывается до замен по ключам (или после плейсхолдеров, но по исходному тексту — уточнить по смыслу). Если fuzzy-match вставляет target, который содержит другой ключ, возможна та же рекурсия; при необходимости ограничить fuzzy-match только теми ключами, у которых target не содержит иных ключей, либо выполнять fuzzy-match на тексте с уже подставленными плейсхолдерами (тогда матчить по плейсхолдерам не будем).

**Зависимости:** нет. Можно делать первым.

## Шаг 2. Zod-схема и нормализация DNA

**Файлы:**  
- `backend/src/services/dnaValidation.ts` (или новый `backend/src/services/dnaSchema.ts`)  
- `backend/src/routes/documents.routes.ts`  
- `backend/src/services/ai.service.ts` (вызовы нормализации перед использованием DNA)

**Что делать:**

2.1. **Схема abbreviationLogic (Zod):**
   - Определить `abbreviationLogicEntrySchema = z.object({ longForm: z.string(), shortForm: z.string() }).strict().optional().catch(...)` или с `.transform()` для приведения строки к объекту.
   - Определить `abbreviationLogicSchema = z.record(z.string(), z.union([z.string(), abbreviationLogicEntrySchema])).transform(normalizeAbbreviationLogicEntries)`.
   - В `normalizeAbbreviationLogicEntries`: любое значение-строка превращать в `{ longForm: s, shortForm: s }`; объект с только `longForm` или только `shortForm` — дополнять недостающее из другого поля или из ключа; объект с `value` — трактовать как longForm и shortForm выводить из ключа или оставить как есть по правилу.

2.2. **Интеграция в валидацию:**
   - В `dnaValidation.ts` (или в модуле схемы): экспортировать функцию **`normalizeDocumentDnaPayload(dna: unknown): DocumentDnaPayload`**, которая прогоняет `dna` через Zod и возвращает уже нормализованный объект (abbreviationLogic только с объектами `{ longForm, shortForm }`).
   - Вызывать `normalizeDocumentDnaPayload` там, где DNA принимается извне (см. шаг 2.3 и 2.4).

2.3. **PUT /documents/:documentId/dna:**
   - В `documents.routes.ts` после `parsed.data` (или вместо прямого `parsed.data`) вызвать `normalizeDocumentDnaPayload(parsed.data)` и сохранять в БД уже нормализованный payload. При ошибке валидации Zod возвращать 400 с перечислением ошибок.

2.4. **Использование DNA в pretranslate и patchTranslate:**
   - В `ai.service.ts` в точках, где берётся DNA из БД для передачи в оркестратор и в `applyTotalCyrillicBan`, один раз прогонять через `normalizeDocumentDnaPayload` (если хотим защититься от уже сохранённых старых данных). Либо считать, что все новые сохранения уже нормализованы (шаг 2.3), и нормализовать только при сохранении.

**Зависимости:** нет. Можно делать параллельно с шагом 1.

## Шаг 3. Явная заморозка DNA при patchTranslate

**Файл:** `backend/src/services/ai.service.ts`

**Что делать:**

3.1. В начале **`patchTranslate`** после загрузки документа и получения `documentDna` через `getDocumentDna(documentId)`:
   - Сохранить DNA в локальную переменную `frozenDna` (или `dnaSnapshot`).
   - Во всём цикле по батчам использовать только эту переменную; нигде в теле цикла не вызывать повторно `getDocumentDna` и не подменять DNA из другого источника.

3.2. Проверить по коду: нет ли внутри цикла `patchTranslate` вызовов, которые перезагружают документ или DNA (например, повторный `prisma.document.findUnique` с `documentDna`). Если есть — заменить на использование `frozenDna`.

3.3. Добавить краткий комментарий в начале блока обработки батчей: «DNA snapshot is frozen at patch start; do not refetch during the run.»

**Зависимости:** нет. Можно делать в любой момент.

## Шаг 4. Pre-flight проверка на циклы и рекурсию

**Файл:** `backend/src/services/dnaValidation.ts` (или `dnaSchema.ts`)

**Что делать:**

4.1. Реализовать **`validateDnaForCycles(dna: DocumentDnaPayload): { valid: boolean; errors: string[] }`**:
   - Обход только `abbreviationLogic`.
   - Для каждого ключа `key` и значения (строка target или `obj.shortForm` / `obj.longForm`): проверить, не содержится ли **сам ключ** (или нормализованная форма ключа) внутри строки value как подстрока или как целое слово. Если да — добавить в `errors`: «Риск рекурсии: ключ "X" содержится в значении».
   - Опционально: построить граф «ключ A → ключи B, которые встречаются в value A». Обход в глубину с проверкой цикла (повторная вершина). При обнаружении цикла добавить ошибку «Обнаружен цикл в abbreviationLogic: A → … → A».

4.2. Вызов валидатора:
   - В **PUT /documents/:documentId/dna** (`documents.routes.ts`): после нормализации вызвать `validateDnaForCycles(normalizedPayload)`. Если `valid === false`, возвращать 400 с сообщениями из `errors`.
   - В **pretranslate** и **patchTranslate** в `ai.service.ts`: перед началом цикла вызвать `validateDnaForCycles(dna)`. При `valid === false` — не запускать перевод, выставить ошибку в progress и вернуть/завершить с сообщением пользователю.

4.3. (Опционально) В UI при сохранении DNA показывать предупреждение (warning), а не блокировать сохранение, если политика — «сохранять с предупреждением». Иначе — блокировать сохранение при `valid === false`.

**Зависимости:** желательно после или вместе с шагом 2 (нормализация), чтобы проверять уже нормализованный объект.

## Шаг 5. Интеграционное тестирование и откат

**Файлы:** тесты (при наличии), ручная проверка.

**Что делать:**

5.1. После шага 1: прогнать сценарий «Retranslate only these» на документе с DNA, где есть ключ с target, содержащим этот ключ (например, ADB → «АБР (ADB)»). Убедиться, что матрёшки нет.

5.2. После шага 2: сохранить DNA с полем-строкой в abbreviationLogic; убедиться, что после сохранения в БД лежит объект `{ longForm, shortForm }`. Прогнать pretranslate/patchTranslate с таким документом.

5.3. После шага 4: сохранить DNA с циклической зависимостью или key-in-value; убедиться, что возвращается 400 или что перевод не стартует с понятным сообщением.

5.4. Подготовить откат: все изменения в отдельных коммитах (или с пометкой в плане), чтобы при необходимости откатить только замену (шаг 1) или только валидацию (шаги 2 и 4).
